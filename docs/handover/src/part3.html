Section 04Access model and credentials

Nothing in the pipeline authenticates to AWS with a long-lived access key. All three GitHub Actions roles are assumed through OIDC federation, scoped by the workflow's own signed identity claim, and expire with the job.

4.1 The three CI roles

Defined in infra/terraform/github-oidc.tf. Each is trusted only for a specific GitHub OIDC subject claim, so a workflow cannot assume a role it was not designed for even if someone edits the workflow file.

RoleTrusted subjectPermitted actions
ocar-prod-gha-deploy repo:…:environment:production ssm:GetParameter/PutParameter on the image-tag parameter only; autoscaling:StartInstanceRefresh/CancelInstanceRefresh on this ASG only; DescribeInstanceRefreshes; ec2:DescribeInstances; ssm:SendCommand + GetCommandInvocation.
ocar-prod-gha-plan repo:…:pull_request Read-only across the services this config manages, plus read/write on the prod/* state prefix and the state KMS key. Never runs on main.
ocar-prod-gha-staging repo:…:environment:staging Full apply/destroy, but only on the staging/* state prefix, /ocar/staging/* parameters, and ocar-staging-* IAM roles.
Detail worth knowing

The deploy role's trust policy matches on environment:production, not on ref:refs/heads/main. This is not arbitrary — when a job declares environment:, GitHub changes the OIDC subject claim format. The ref-based condition was tried first, failed, and the actual rejected claim was read out of CloudTrail to determine the correct form. If you add a new deploy job, it must declare the same environment or the assume-role will fail.

4.2 The EC2 instance role

Instances assume ocar-<env>-ec2-role (infra/terraform/iam.tf). It grants ssm:GetParameter on exactly six named parameters and kms:Decrypt on the alias/aws/ssm key — nothing broader:

  • /ocar/<env>/image-tag — which image version to run
  • /ocar/<env>/ghcr-token — GHCR pull credential (SecureString)
  • /ocar/<env>/api-env — the application's entire environment file (SecureString)
  • /ocar/<env>/migration-database-url — direct DB URL for migrations (SecureString)
  • /ocar/<env>/docker-compose-prod — Compose file, Terraform-managed
  • /ocar/<env>/alloy-config — Alloy config, Terraform-managed

The AWS-managed AmazonSSMManagedInstanceCore policy is also attached. Its inline comment still describes it as temporary debugging access, which is now out of date — the deploy pipeline routes database migrations to a live instance through ssm:SendCommand, and that requires the instance to be a registered SSM managed instance. Removing this attachment would break every deploy. See gap G-04.

Operational safety

Three destructive capabilities exist and have no confirmation gate today. Please read gaps G-05 and G-06 before using them: running staging-infra.yml with action: destroy executes terraform destroy -auto-approve against real infrastructure with no approval step; a push directly to main bypasses review entirely; and a merge to main that touches api/** deploys to production automatically with no human pause.

4.4 Getting a shell on an instance

SSH is not open. Use SSM Session Manager, which is authenticated by IAM and audited in CloudTrail: 

# list instances belonging to the ASG
aws ec2 describe-instances \
  --filters "Name=tag:aws:autoscaling:groupName,Values=<ASG_NAME>" \
             "Name=instance-state-name,Values=running" \
  --query 'Reservations[].Instances[].[InstanceId,PrivateIpAddress,Placement.AvailabilityZone]' \
  --output table

# open a shell
aws ssm start-session --target <INSTANCE_ID>

# once inside — the app lives here
cd /opt/ocar
sudo docker compose -f docker-compose.prod.yml ps
sudo docker logs --tail 200 -f ocar_api
sudo cat /var/log/user-data.log   # full boot transcript
Note

/var/log/user-data.log is the single most useful file when an instance fails to become healthy. The boot script runs under set -x, so it contains a complete trace of every step — with credential assignments explicitly untraced so tokens never land in the log.

Section 05Continuous integration

.github/workflows/ci.yml. Seven independent jobs, no dependency edges between them, all starting simultaneously. Triggered on every push to every branch and on every pull request targeting main.

5.1 Job reference

5.2 Design points

ChoiceWhy
Trivy pinned to a commit SHA aquasecurity/trivy-action@ed142fd0… rather than @v0.36.0. Version tags on that action were force-pushed during a March 2026 supply-chain incident; a mutable tag is not a trustworthy reference for a security-scanning step.
Dependency scan is CRITICAL-only The monorepo carries roughly 27 pre-existing HIGH transitive findings, mostly DoS-class and largely in frontend packages. Gating on them would block every pull request indefinitely and train the team to ignore the scanner. Secrets and misconfiguration — where a finding is nearly always real and actionable — stay at HIGH. This is a conscious, revisitable trade-off, recorded as G-15.
Migrations run in CI against a real Postgres A migration that fails to apply cleanly fails the build before it can reach production. This is the only place the full migration chain is exercised from empty on every change.
Per-job concurrency with cancel-in-progress Pushing twice in quick succession cancels the superseded run per job, saving runner minutes without cancelling unrelated branches.
Node 22, pnpm 9, frozen lockfile --frozen-lockfile means CI fails rather than silently resolving a different dependency tree than the one committed.
Known weakness

Test coverage is thin. Five test files exist in the API — four covering ride assignment and broadcast, one covering maintenance middleware — and there are none for payments, authentication, OTP, wallet or settlement. vitest and @vitest/coverage-v8 are installed and a test:coverage script exists, but no coverage threshold is enforced in CI. Recorded as G-13. The pipeline is production-grade; the test suite it runs is not yet.
