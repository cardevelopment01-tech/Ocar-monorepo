17.2 Detail on the high-severity items

G-01 — The health endpoint cannot fail

api/src/app.ts checks database and Redis connectivity, reports the result in the response body, and then unconditionally returns HTTP 200: 

const [dbOk, redisOk] = await Promise.all([testConnection(), testRedis()])
res.status(200).json({ status: 'ok', db: dbOk ? 'ok' : 'error', … })

The ALB target group matches on 200. An instance whose database connection has failed therefore remains healthy and continues receiving traffic indefinitely. The ASG will not replace it. The deploy pipeline's health check will pass.

The smoke test against /api/v1/geo/cities is currently the only automated check that would catch this, and it runs once per deploy rather than continuously. Suggested fix: return 503 when dbOk is false, keeping the diagnostic body intact. Consider whether Redis failure should also fail the check — it degrades real-time delivery but leaves core HTTP working, so it may warrant a separate readiness endpoint rather than the same one.

G-02 — Staging cannot be provisioned through CI

rds.tf was added to the shared configuration, but the ocar-prod-gha-staging role's policy in github-oidc.tf grants only ec2, elasticloadbalancing, autoscaling, elasticache and acm. There is no rds:* statement, and no secretsmanager:* — which manage_master_user_password also requires.

A staging apply will proceed until it reaches the database resources and then fail on AccessDenied. Because this is the environment the load test depends on, this blocks OPS-09, which in turn blocks the load test, which in turn blocks the capacity validation the entire scale-readiness report defers to.

G-05 / G-06 — Missing approval gates

Three protections referenced in the workflows do not actually exist:

DeclaredRealityConsequence
environment: production in deploy.ymlEnvironment never createdDeploys to production run with no human approval pause.
environment: staging in staging-infra.ymlEnvironment never createdterraform destroy -auto-approve can be dispatched by anyone with workflow-run access.
Branch protection on mainNot configuredA direct push bypasses review. CI still gates deploy, but nothing gates merge.

All three require repository admin rights, which the account used to build this pipeline does not hold (gh api repos/:owner/:repo --jq '.permissions' returns admin: false). The exact gh api commands to close each are documented in CLAUDE.md under "Pending Ops Actions". This is the single highest-value item on this list for whoever holds admin rights — it is minutes of work and closes three distinct paths to unreviewed production change.

G-14 — Admin TOTP enforcement is bypassed

api/src/middleware/auth.middleware.ts line 125: 

// TODO(SHIP-BLOCKER): hardcoded bypass, see TOTP_DEV_NOTE.md — remove before shipping
const mustEnrollTotp = false && MANDATORY_TOTP_ROLES.has(adminRole) && !totpEnabled

The leading false && short-circuits the entire expression, so super_admin and finance_admin accounts are never required to enrol in two-factor authentication despite the surrounding logic being complete and correct. The enrolment endpoints work; the enforcement is simply switched off. The comment marks it as a ship blocker. It is flagged here because these are the roles with the broadest access in the system.

G-13 — Test coverage

Five test files exist in the API — four covering ride assignment and broadcast, one covering maintenance middleware. There are none for payments, wallet, settlements, authentication, OTP, safety or ride chat. vitest and @vitest/coverage-v8 are installed and pnpm test:coverage is defined, but CI runs pnpm test with no threshold.

This is worth stating plainly: the delivery pipeline is well-built and the gates are structurally sound, but a gate is only as strong as the checks behind it. Payments and authentication are the two areas where a regression is most expensive and where there is currently no automated protection at all.

17.3 Notes on selected medium and low items

RefDetail
G-04 The comment above aws_iam_role_policy_attachment.ssm_session_manager_debug in iam.tf describes it as temporary debugging access to be removed once boot is confirmed working. That is now wrong and dangerous — deploy.yml routes migrations through ssm:SendCommand, which requires instances to be registered SSM managed instances. Acting on the comment would break every deploy. The attachment should stay; the comment must be corrected.
G-07 min_size, desired_capacity and max_size are literals in asg.tf, not variables. Staging therefore provisions the same 2/2/4 fleet as production. For a load-test environment that is arguably correct — the numbers must be comparable — but it removes the option of a cheaper single-instance staging for functional testing.
G-08 The VPC, subnets, internet gateway, route table and the two core security groups are named ${var.project_name}-* without the environment segment, unlike every other resource. Both environments would produce identically-named resources. They live in separate VPCs and separate state, so nothing collides functionally — but console navigation with both environments running is needlessly confusing.
G-17 cAdvisor and the ocar_api resource limits are committed to docker-compose.prod.yml, which reaches instances through an SSM parameter sourced from that file at terraform apply time. Until an apply runs and the fleet rolls, running instances do not have them. Applying also requires re-importing infra/grafana/dashboards/ocar-overview.json for the per-container row to render.
G-18 No deregistration_delay is set on the target group, so it uses the AWS default of 300 seconds. For long-lived WebSocket connections this is generous rather than insufficient — the concern with an unset value is usually the opposite. Worth setting explicitly so the value is visible in code rather than implied.

17.4 Suggested order of work

  1. G-06, G-05 — create the GitHub Environments and branch protection. Minutes of work, closes three unreviewed-change paths. Requires admin.
  2. G-01 — make /health return 503 on database failure. A few lines, and it is what makes the ASG's self-healing actually cover a real failure mode.
  3. G-14 — remove the TOTP bypass, or record an explicit decision to defer it with a date.
  4. G-02, G-03 — add the missing IAM permissions. Unblocks staging, which unblocks the load test.
  5. Load test — resolves G-09 and G-16 with data rather than estimates, and validates the capacity claims in the readiness report.
  6. G-13 — payments and auth test coverage. The largest effort here, and the one that most changes the pipeline's real value.
  7. G-11, G-04 — reconcile the documentation with reality.

C — Glossary

TermMeaning in this system
Instance refreshThe EC2 Auto Scaling mechanism that replaces instances in a group according to a policy. Used here for both deploys and infrastructure changes.
Launch before terminatingReplacement method triggered by MinHealthyPercentage = 100: a new instance must be healthy before the old one is terminated.
Target trackingScaling policy type where AWS maintains a metric at a target value and manages the alarms itself.
ALBRequestCountPerTargetRequests per healthy target per one-minute period. Target value 1000 ≈ 16.7 req/sec per instance.
Deregistration delayHow long the load balancer lets in-flight work finish on a target being removed. 300 s here.
Health check grace periodHow long a newly launched instance is exempt from health evaluation. 240 s here.
OIDC federationShort-lived AWS credentials issued against a signed GitHub identity token, replacing stored access keys.
DriftDivergence between real infrastructure and Terraform state. Created deliberately by OPS-04; otherwise a problem.
Forward-only migrationSchema changes are never reverted. A bad migration is corrected by a new one.
