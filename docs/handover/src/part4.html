Section 06Continuous delivery

.github/workflows/deploy.yml. Three jobs — changes, build-push, deploy — chained by needs:. Triggered by workflow_run when the CI workflow completes on main, and gated on that run having concluded successfully.

6.1 Step-by-step, with the reasoning

Step 1 — Change detection

workflow_run triggers do not support on.paths: filtering, so this job implements it manually. It queries the Deploy workflow's own run history for the last successful deploy's commit SHA and diffs against that, falling back to HEAD^ only if no prior successful run exists.

Deployment proceeds only if the diff touches one of:

api/            pnpm-lock.yaml      pnpm-workspace.yaml
package.json    .github/workflows/deploy.yml

Two real incidents shaped this. First, an earlier version of the filter included infra/** and docker-compose.prod.yml; an infrastructure-only pull request that added an IAM role rebuilt the image and cycled the entire ASG for nothing. Neither path is ever copied into the image — api/Dockerfile only COPYs the lock files, the root package.json, and api/. Second, diffing against HEAD^ instead of the last deployed SHA silently skipped five commits when someone pushed six commits directly to main and only the last was documentation.

Step 2 — Build and push

Multi-stage build from api/Dockerfile. Four stages: install all dependencies, compile TypeScript, produce a symlink-free production node_modules via pnpm deploy --prod, then assemble a minimal node:22.16-alpine runtime image. The final image runs as the non-root node user and carries its own HEALTHCHECK.

Images are tagged sha-<short-sha>, plus latest on the default branch. The immutable SHA tag is what the deployment actually references — latest exists for convenience only and is never what an instance boots from.

Steps 4–5 — Migrations, and why they run through SSM

RDS is not publicly reachable; only the EC2 security group can open port 5432. A GitHub-hosted runner therefore cannot connect to the database directly. Rather than punch a hole in the security group or introduce a bastion, the workflow finds a live ASG instance and asks SSM to run the migration container there: 

docker run --rm --name db_migrate \
  -e MIGRATION_DATABASE_URL="$DB_URL" \
  --entrypoint node ghcr.io/<owner>/ocar-api:<tag> dist/db/migrate.js

Three properties of this arrangement are worth understanding:

  • No secret crosses the runner. The instance reads the database URL from SSM itself using its own IAM role. The command text sent by the workflow contains a parameter name, never a value.
  • Migrations run against the new image but before the rollout. The old application version is still serving every request while this happens, which means migrations must be backward-compatible with the currently-running code. Additive changes are safe; dropping or renaming a column that live code still reads is not.
  • --name db_migrate is load-bearing. Without an explicit name, Docker assigns a random one, cAdvisor discovers it as a new container, and every deploy permanently added active series to the Grafana Cloud metrics tenant. That caused a real cardinality incident on 19 August 2026. Alloy's relabel rules now keep only containers matching ocar_*, so this container is filtered out by name.
Idempotency

dist/db/migrate.js also runs on every container start via api/entrypoint.sh. So on a normal deploy the migration runner executes several times — once from this step, then once per replacement instance. This is safe because the runner skips already-applied files and serialises concurrent invocations with a pg_advisory_lock. The explicit step exists purely to gate the rollout on migration success rather than discovering a failure one instance at a time.

Steps 6–7 — Tag swap and refresh

The current value of /ocar/prod/image-tag is captured first — this is the rollback anchor, and capturing it before overwriting is the entire reason automatic rollback is possible. The new tag is then written, and an instance refresh is started. Note that instances read the tag only at boot; writing the parameter changes nothing until instances are replaced.

The certificate is issued for the domain, not for the ALB hostname, so verification is skipped deliberately at this step; the header is what makes the request route correctly.

The smoke test matters more than the health check. As documented in gap G-01, /health currently returns HTTP 200 even when the database is unreachable — so the smoke test is the only step in the pipeline that genuinely proves the database path works end to end.

Step 12 — Rollback

Any failure at steps 9, 10 or 11 restores the previously recorded tag and starts a second instance refresh, then exits non-zero. Two limits apply:

  • Migrations are not reverted. Schema changes are forward-only. If the migration itself is the fault, it must be fixed with a new migration, not undone.
  • Rollback depth is one. Only the immediately preceding tag is recorded. Going back further is a manual operation — procedure OPS-02.

Section 07Deployment strategy and its alternatives

The strategy is a rolling replacement with launch-before-terminate, implemented through EC2 Auto Scaling instance refresh. It is not blue/green and not canary. This section explains precisely what it does, and why the alternatives were not chosen.

7.1 What 100 / 100 actually means

Both asg.tf and the deploy workflow set MinHealthyPercentage = 100 and MaxHealthyPercentage = 100. Per AWS's documentation, setting the minimum healthy percentage to 100 changes the replacement method to launch before terminating: a replacement instance is launched and must pass health checks before the instance it replaces is terminated. Setting both values to 100 additionally constrains the group to replacing one instance at a time.

The practical consequence is that serving capacity never drops below the desired count during a deploy. Any other combination permits a dip — with min = 50 on a two-instance group, capacity can legitimately fall to one instance mid-deploy.

7.3 Why not blue/green

Blue/green stands up a complete parallel environment, shifts traffic at the load balancer, and keeps the old environment ready for an instant switch back. It is the right answer in several situations. None of them currently apply here, and one of them actively argues against it:

DimensionRolling refresh (current)Blue/green
Extra compute during deployOne additional instance, for a few minutesA full duplicate fleet, for the whole cutover window
Rollback speedMinutes — requires a second rolling refreshSeconds — flip the listener back
Database compatibilityBoth versions run simultaneously; migrations must be backward-compatibleSame constraint. Both fleets share one database — blue/green does not solve this
Long-lived WebSocketsDrains per instance, gradually, over the deregistration delayCutover disconnects every socket on the blue fleet at once
Moving partsOne AWS-native primitive already in use for scalingDuplicate target groups, listener-swap automation, environment-tracking state

The database row is the decisive one. The most commonly cited benefit of blue/green — instant, safe rollback — is materially weaker here because both fleets would share a single RDS instance. A schema change that breaks the old version breaks it whether that version is running on the green fleet or the blue one. The forward-only migration constraint documented in §6.1 is a property of sharing one database, not a property of rolling deploys, and switching strategies would not remove it.

The WebSocket row is the second. Ocar's traffic is dominated by long-lived Socket.io connections carrying live driver locations. A rolling replacement disconnects a fraction of clients per instance, spread over the deploy, and each reconnects to a healthy target within seconds. An atomic blue/green cutover disconnects every connected rider and driver simultaneously.

When to revisit

Blue/green becomes worth the additional machinery when deploys are frequent enough that multi-minute rollback is a genuine business cost, or when the fleet is large enough that a rolling replacement takes more than about half an hour. Neither is true at two to four instances. Canary — routing a weighted percentage to a new version via ALB weighted target groups — is the more natural next step, and would layer onto the existing setup without replacing it.

7.4 Deploys triggered by infrastructure changes

There is a second, easily-missed path to a rolling replacement. The ASG's launch_template block references aws_launch_template.api.latest_version — a real numeric version, not the literal string $Latest. Any Terraform change that produces a new launch template version (a new AMI, a different instance type, an edited boot script) therefore appears as a genuine diff on the ASG, and the instance_refresh block causes terraform apply to roll the whole fleet automatically.

Important

This means terraform apply can restart your entire production fleet. It is intended behaviour — without it, a launch template change would silently apply only to instances that happened to be replaced later for unrelated reasons. But it makes reading the plan output before applying non-optional. If the plan shows a change to aws_launch_template.api, expect a full rolling replacement.
