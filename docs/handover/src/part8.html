OPS-08 Apply any other infrastructure change Routine · Terraform · varies

Blast radius: depends entirely on the plan. Read it. Reversal: revert and re-apply.

  1. Make the change in infra/terraform/*.tf on a branch.
  2. Open a pull request. The plan is posted as a PR comment automatically.
  3. Read the plan against this checklist before merging:
    • Does it show aws_launch_template.api changing? → the fleet will roll.
    • Does it show aws_elasticache_replication_group being replaced? → the cache will be destroyed and recreated. Contents are disposable, but expect an interruption to real-time delivery and queued jobs.
    • Does it show aws_db_instance being replaced? → stop. That is data loss. Deletion protection should prevent it in prod, but do not rely on that.
    • Does it show anything being destroyed that you did not intend to destroy?
  4. Merge, then apply from a workstation: 
    pnpm infra:prod:init
pnpm infra:prod:plan
pnpm infra:prod:apply

Infrastructure never auto-applies on merge. Only the plan runs in CI. This is deliberate — AWS changes are not cheaply reversible the way an application deploy is.

OPS-09 Stand up the staging environment Occasional · ~20–25 min

Blast radius: creates a second full environment and its cost. Reversal: OPS-10.

  1. Create the DNS record for staging.ocar-api.clienttesting.in in Cloudflare. ACM validation will block the apply until the validation CNAME resolves publicly — it must be DNS-only, not proxied.
  2. Seed the four hand-maintained SSM parameters under /ocar/staging/: image-tag, ghcr-token, api-env, migration-database-url. Use non-production credentials throughout — Razorpay test keys, a distinct JWT secret.
  3. Run the workflow: Actions → Staging Infra (apply/destroy) → Run workflow → action: apply. Or locally: 
    pnpm infra:staging:init
pnpm infra:staging:plan
pnpm infra:staging:apply
  4. Point the Cloudflare record at the staging ALB DNS name from the apply output.
  5. Full step-by-step for the manual, non-Terraform portions: docs/superpowers/specs/2026-08-14-staging-runbook.md.
Known blocker

The ocar-prod-gha-staging IAM role grants no rds:* permissions, but rds.tf is part of the shared configuration. A staging apply through the workflow will therefore fail when it reaches the database resources. This must be fixed before OPS-09 can complete via CI — see G-02. A local apply with broader credentials is the current workaround.

OPS-10 Tear down staging Occasional · destructive · ~10 min

Blast radius: destroys the entire staging environment. Reversal: OPS-09 from scratch.

  1. Verify which environment you are targeting. Terraform reuses whatever backend the local .terraform/ directory was last initialised against: 
    terraform init -reconfigure -backend-config=staging.backend.hcl
terraform state list | head
  2. Destroy: 
    pnpm infra:staging:destroy

    Or the workflow with action: destroy.

  3. Remove the Cloudflare DNS records for the staging hostname.
  4. Confirm nothing survived — orphaned ElastiCache nodes and RDS instances are the expensive ones: 
    aws rds describe-db-instances --query 'DBInstances[].DBInstanceIdentifier'
aws elasticache describe-replication-groups --query 'ReplicationGroups[].ReplicationGroupId'
No confirmation gate exists

The workflow's environment: staging declaration is inert — the GitHub Environment was never created. A destroy dispatch runs terraform destroy -auto-approve against real infrastructure with no approval step and no undo. See G-05. Always destroy after a load test; staging is not meant to run continuously and costs the same per-instance rate as production.

OPS-11 Replace a single unhealthy instance Incident · ~5 min

Blast radius: one instance. Reversal: none needed — the ASG relaunches automatically.

  1. Identify it: 
    aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names <ASG_NAME> \
  --query 'AutoScalingGroups[0].Instances[].{Id:InstanceId,State:LifecycleState,Health:HealthStatus,AZ:AvailabilityZone}' \
  --output table
  2. Look before you kill it — the cause is usually in the boot log or the container log: 
    aws ssm start-session --target <INSTANCE_ID>
sudo tail -100 /var/log/user-data.log
sudo docker ps -a
sudo docker logs --tail 200 ocar_api
  3. Terminate it and let the ASG replace it. --should-decrement-desired-capacity false is what makes the replacement happen: 
    aws autoscaling terminate-instance-in-auto-scaling-group \
  --instance-id <INSTANCE_ID> \
  --no-should-decrement-desired-capacity
  4. Confirm the replacement reaches InService and Healthy. Allow at least the 240-second grace period plus three 15-second health checks.

If replacements repeatedly fail to become healthy, the problem is systemic — a bad image, a broken SSM parameter, or an unreachable dependency. Go to OPS-12 rather than cycling instances.

OPS-12 Diagnose a failed or stuck deploy Incident · investigation

Blast radius: read-only until you choose an action.

  1. Locate the failing step in the Deploy workflow run. The step name maps directly onto Figure 4.
  2. Migration step failed → the rollout never started and production is untouched, still running the previous version. Read the captured stdout/stderr in the workflow log. Fix the migration and merge again. Do not attempt to force the rollout past it.
  3. Refresh timed out or failed → replacement instances are not becoming healthy: 
    aws autoscaling describe-instance-refreshes \
  --auto-scaling-group-name <ASG_NAME> --max-records 1 \
  --query 'InstanceRefreshes[0].{Status:Status,Reason:StatusReason,Pct:PercentageComplete}'
    Then shell into a failing instance and read /var/log/user-data.log. The usual causes are a GHCR pull failure (expired ghcr-token), a malformed api-env, or the application exiting at startup because it cannot reach RDS or Valkey.
  4. Health check failed but the refresh succeeded → instances are healthy at the target group but the ALB is not serving correctly. Check target health directly: 
    aws elbv2 describe-target-health --target-group-arn <TG_ARN>
  5. Smoke test failed but health passed → this is the important case. It means the process is alive but the database path is broken, which /health does not currently detect (G-01). Check RDS availability, the security group, and DATABASE_URL in api-env.
  6. To stop an in-progress refresh: 
    aws autoscaling cancel-instance-refresh --auto-scaling-group-name <ASG_NAME>

    Cancelling leaves the group in a mixed state — some instances on the new version, some on the old. Follow immediately with OPS-02 to converge on a known-good tag.

Section 15Failure modes and recovery

What breaks, what it looks like, and what to do. Ordered by how likely each is to occur.

FailureObservable signalAutomatic responseAction
One instance dies Target group shows one unhealthy target; no user-visible impact ASG terminates and replaces it; ALB stops routing to it after 3 failed checks None required. Investigate the cause via OPS-11 if it recurs.
Bad deploy Deploy workflow red at the health or smoke step Automatic rollback to the previous tag, plus a second refresh Confirm the rollback completed. Diagnose with OPS-12.
Bad migration Deploy fails at the migration step Rollout never starts; production untouched Fix forward. Never attempt to revert a migration.
CPU credits exhausted CPUCreditBalance near zero; latency rising with no scaling activity None — request-count scaling may still fire, CPU-based would not Enable Unlimited mode, or move to a fixed-performance type (OPS-07).
Valkey node fails Real-time updates stop; BullMQ stalls; rate limiting fails open or closed None — single node, failover disabled Replace the node. Cache contents are disposable; this is an outage, not data loss.
RDS unavailable Smoke test fails; /health reports db: "error" in its body but still returns HTTP 200 None — single-AZ, no replica. The ALB does not detect this Check the RDS console. Restore from automated backup if required. See G-01 and G-10.
Entire AZ fails Half the fleet unhealthy ALB routes to the surviving AZ; ASG launches replacements there Monitor. If RDS was in the failed AZ, the database is down until AWS recovers it — single-AZ is an accepted risk.
Grafana Cloud cap exceeded Billing-usage alert at 85%; metrics or logs start being dropped Alert fires Review cardinality (§13.2) before assuming an upgrade is needed. Both prior incidents were cardinality, not genuine volume.
GHCR token expired Every new instance fails to become healthy; docker login error in user-data.log None — the ASG will cycle instances indefinitely Rotate /ocar/prod/ghcr-token, then refresh (OPS-06 steps 4–5).
The pattern worth internalising

Every failure the platform recovers from automatically is one where an instance is the failing unit. Every failure requiring manual intervention is one where a shared singleton fails — the Valkey node, the RDS instance, an SSM parameter. That is the accurate summary of this architecture's resilience profile: the compute tier is genuinely redundant; the data tier is not.

Section 16Load testing

A k6 suite exists at load-tests/, built to exercise the specific numbers committed in the scale-readiness report: 5,000–6,000 concurrent connections, GPS pings every three to five seconds, and booking bursts on top.

16.1 Structure

PathPurpose
seed/generate-test-tokens.jsMints JWTs directly rather than driving real OTP flows — thousands of logins would cost real money in SMS and hit Fast2SMS rate limits. Creates synthetic riders; reuses real onboarded drivers and stamps their daily verification records.
seed/generate-bulk-ride-history.jsPopulates history so read paths are exercised against realistic table sizes.
k6/lib/socketio.jsHand-rolled Engine.IO v4 / Socket.io v4 client. k6 runs its own JS runtime, so the real socket.io-client package cannot be used.
k6/smoke.jsSingle-VU sanity check across every code path. Run before every session.
k6/main.jsThe full test — concurrent booking, driver GPS and idle-rider scenarios.
k6/spike.js, k6/accept-race.jsSudden-surge behaviour, and concurrent ride-acceptance contention.
verify/reconcile.js, verify/query-regression.jsPost-run data-integrity and query-performance verification.

16.2 Method

  1. Stand up staging (OPS-09) — note the blocker recorded there.
  2. Seed data and tokens.
  3. Run smoke.js privately first. A live run should never be the script's first contact with the environment.
  4. Step up in stages rather than starting at target load: roughly 200 → 1,000 → 3,000 → 6,000 connections.
  5. Watch, in order of expected constraint: Valkey ops/sec and connections; RDS connection count and Performance Insights; CPUCreditBalance; the cAdvisor per-container row; ALB 5xx rate and p95 latency.
  6. Tear staging down afterwards (OPS-10).
