Section 13Observability

One agent per instance ships logs, metrics and traces to one platform. Grafana Alloy (ocar_alloy) reads from the Docker socket and from three exporters, and forwards to Grafana Cloud — Loki for logs, Mimir for metrics, Tempo for traces.

13.1 Signals

SignalSourceDestinationNotes
LogsPino JSON on container stdoutLokiExactly four indexed labels — container, service, env, host. Everything else, including requestId, stays in the JSON body and is queried rather than indexed.
App metricsprom-client at /metricsMimirhttp_request_duration_seconds, pg_pool_connections, bullmq_queue_job_counts.
Host metricsnode-exporterMimirCPU, memory, disk, network per instance.
Container metricscAdvisorMimirAggressively filtered — see below.
Database metricspostgres-exporterMimirIncludes pg_stat_statements. Every instance reports identical numbers; dashboards use max() not sum().
TracesOpenTelemetry SDK → Alloy OTLPTempoThe app sends to alloy:4318, never directly to Grafana Cloud, so credentials live only in Alloy.

Log and trace correlation works because the tracing SDK's trace_id feeds Pino's mixin — every log line carries the ID of the span it was emitted within, so a trace in Tempo can be pivoted to its logs in Loki.

13.2 Cardinality controls — read before editing config.alloy

Two incidents shaped the current relabelling rules, and both are easy to reintroduce:

  • 18 August 2026. cAdvisor's roughly 100 metric families, multiplied across a rolling replacement, tipped the Grafana Cloud tenant's active-series cap. The fix keeps only five metric families, grepped from the dashboard that actually queries them.
  • 19 August 2026. The deploy pipeline's migration container was launched with a random name, so cAdvisor discovered a new container on every deploy and permanently inflated the series count. The fix is two-part: the container is now explicitly named db_migrate, and Alloy keeps only containers matching ocar_*.

A labelkeep rule then retains only __name__, name and host, which eliminates churn from container IDs and image tags in one rule rather than a drop-list that must be maintained.

Practical consequence

Adding a container to docker-compose.prod.yml whose name does not start with ocar_ means it will not appear in metrics at all. That is usually what you want, but it is silent — nothing warns you.

Do not hand-edit in the Grafana UI

grafana_notification_policy is a whole-tree resource — applying it replaces the entire policy. Any change made in the Grafana interface will be silently destroyed by the next terraform apply. All notification routing changes must go through the Terraform module.

Section 14Operational procedures

Twelve numbered procedures covering every routine and emergency operation. Each states its blast radius and how to reverse it. Shared prerequisites: AWS CLI authenticated against ap-south-1, Terraform 1.15.8, repository checked out, working directory infra/terraform for anything Terraform-related.

OPS-01 Deploy application code Routine · automatic · ~10–15 min

Blast radius: production fleet rolled one instance at a time. No capacity dip. Reversal: automatic on failure; manual via OPS-02.

  1. Merge to main. Nothing else is required — the pipeline is fully automatic.
  2. Watch the CI workflow. All seven jobs must pass or Deploy never starts.
  3. Watch the Deploy workflow. If the Detect relevant changes job reports relevant=false, the change did not touch anything that reaches the image and no deploy is needed — this is correct behaviour, not a fault.
  4. Observe the rollout while it runs: 
    watch -n 15 'aws autoscaling describe-instance-refreshes \
  --auto-scaling-group-name <ASG_NAME> --max-records 1 \
  --query "InstanceRefreshes[0].{Status:Status,Pct:PercentageComplete}" --output table'
  5. Confirm afterwards: 
    curl -s https://ocar-api.clienttesting.in/health | jq
curl -s https://ocar-api.clienttesting.in/api/v1/geo/cities | jq '.[0]'

If a migration is involved: it runs before any instance is replaced and gates the rollout. It must be backward-compatible with the currently-running code, because the old version keeps serving traffic throughout — see §6.1.

OPS-02 Roll back to a specific image version Emergency · manual · ~10–15 min

Blast radius: full fleet roll. Reversal: repeat with the newer tag.

  1. Identify the target tag. Tags are sha-<short-sha> and are listed on the GHCR package page, or in the Docker metadata step of a previous Deploy run.
  2. Record what is currently deployed, so this step is itself reversible: 
    aws ssm get-parameter --name /ocar/prod/image-tag --query 'Parameter.Value' --output text
  3. Point the parameter at the target version: 
    aws ssm put-parameter --name /ocar/prod/image-tag \
  --type String --value "sha-abc1234" --overwrite
  4. Roll the fleet so instances actually pick it up: 
    aws autoscaling start-instance-refresh \
  --auto-scaling-group-name <ASG_NAME> \
  --preferences '{"MinHealthyPercentage":100,"MaxHealthyPercentage":100}'
  5. Verify as in OPS-01 step 5.
Migrations are not reverted

Schema changes are forward-only. Rolling the image back does not undo a migration. If the migration is the fault, the old code will now be running against a newer schema — which may be worse than the problem you are fixing. Fix forward with a new migration instead.

OPS-03 Enable or disable maintenance mode Emergency · manual · ~1–2 min

Blast radius: every request receives HTTP 503 immediately. Reversal: re-apply with the flag false.

  1. Enable: 
    terraform apply -var="environment=prod" -var maintenance_mode=true
  2. Confirm the fixed response is being served: 
    curl -i https://ocar-api.clienttesting.in/api/v1/geo/cities

    Expect 503 with "code":"MAINTENANCE_MODE".

  3. Disable when finished: 
    terraform apply -var="environment=prod" -var maintenance_mode=false

Health checks are unaffected — ELB probes registered targets directly rather than through listener rules, so instances continue to be evaluated normally while the rule is active. Use this when the fleet itself may be unavailable and the application-level maintenance flag cannot run.

OPS-04 Temporarily add capacity for a known event Planned · manual · ~5 min · creates drift

Blast radius: adds instances and cost. Reversal: mandatory — see step 4.

  1. Check the current bounds: 
    aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names <ASG_NAME> \
  --query 'AutoScalingGroups[0].{Min:MinSize,Desired:DesiredCapacity,Max:MaxSize}' --output table
  2. Raise desired capacity. It must stay within the existing min/max, so raise --max-size in the same call if you need to exceed 4: 
    aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name <ASG_NAME> \
  --min-size 4 --desired-capacity 4 --max-size 6

    Raising --min-size too is deliberate: it stops the target-tracking policy from immediately scaling back in while traffic is still low, just before the event starts.

  3. Confirm the new instances reach InService — typically four to five minutes: 
    aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names <ASG_NAME> \
  --query 'AutoScalingGroups[0].Instances[].{Id:InstanceId,State:LifecycleState,Health:HealthStatus}' \
  --output table
  4. Restore afterwards. Either repeat step 2 with the original values, or run terraform apply, which will reset them to whatever asg.tf declares.
This creates Terraform drift on purpose

Terraform still believes the group is 2/2/4. Anyone running terraform apply for an unrelated reason will silently revert your change — possibly mid-event. Announce it, and set a reminder to restore it yourself.

OPS-05 Change the scaling bounds permanently Planned · Terraform · ~5 min

Blast radius: capacity change only — no instance replacement, provided the launch template is untouched. Reversal: revert the commit and re-apply.

  1. Edit min_size, desired_capacity or max_size in infra/terraform/asg.tf.
  2. Open a pull request. terraform-plan.yml posts the plan as a PR comment automatically for any change under infra/**.
  3. Read the plan. It should show only the ASG changing. If it also shows aws_launch_template.api changing, expect a full rolling replacement (§7.4).
  4. Merge, then apply from a workstation — infrastructure does not auto-apply on merge: 
    pnpm infra:prod:init    # once per session, or after switching environments
pnpm infra:prod:plan
pnpm infra:prod:apply
  5. Consider whether target_value on the scaling policy also needs adjusting — raising max_size without retuning the threshold changes the ceiling but not the trigger point.
OPS-06 Change an environment variable or secret Routine · manual · ~15 min · handles plaintext secrets

Blast radius: full fleet roll at step 5. Reversal: keep the pre-edit copy until verified.

  1. Pull the current value to a file. Do this in a directory that is not the repository: 
    cd $(mktemp -d)
aws ssm get-parameter --name /ocar/prod/api-env --with-decryption \
  --query 'Parameter.Value' --output text > api-env.txt
cp api-env.txt api-env.backup.txt   # rollback copy
  2. Edit api-env.txt. Change only the line you intend to change — the entire blob is replaced, so an accidental edit elsewhere ships silently.
  3. Diff before pushing. This step is not optional; it is what would have caught the 12 August 2026 REDIS_URL incident: 
    diff api-env.backup.txt api-env.txt
  4. Push the whole value back: 
    aws ssm put-parameter --name /ocar/prod/api-env --type SecureString \
  --value "$(cat api-env.txt)" --overwrite
  5. Roll the fleet — running instances read SSM only at boot and will not otherwise notice: 
    aws autoscaling start-instance-refresh \
  --auto-scaling-group-name <ASG_NAME> \
  --preferences '{"MinHealthyPercentage":100,"MaxHealthyPercentage":100}'
  6. Verify, then destroy the plaintext copies: 
    curl -s https://ocar-api.clienttesting.in/health | jq
shred -u api-env.txt api-env.backup.txt 2>/dev/null || rm -f api-env.txt api-env.backup.txt
OPS-07 Change the EC2 instance type Planned · Terraform · ~15 min · rolls the fleet

Blast radius: full rolling replacement. Reversal: revert the variable and apply again — another full roll.

  1. Confirm the target type is the same CPU architecture. If moving to Graviton, stop and read §10.3 — that is a multi-part change, not this procedure.
  2. Change the default of instance_type in infra/terraform/variables.tf, or pass it at apply time for a one-off test.
  3. Plan and read the output. Expect aws_launch_template.api to show a new version and the ASG to show a corresponding change: 
    pnpm infra:prod:init
pnpm infra:prod:plan
  4. Consider raising mem_limit and cpus in docker-compose.prod.yml in the same change if you are moving to a larger instance — otherwise the extra memory is unusable (§10.4).
  5. Apply. This triggers a rolling replacement automatically; there is no separate refresh step: 
    pnpm infra:prod:apply
  6. Watch the refresh as in OPS-01 step 4, then confirm the new type is live: 
    aws ec2 describe-instances \
  --filters "Name=tag:aws:autoscaling:groupName,Values=<ASG_NAME>" \
             "Name=instance-state-name,Values=running" \
  --query 'Reservations[].Instances[].[InstanceId,InstanceType]' --output table
  7. Watch CPU, memory and — if still on a t3 — CPUCreditBalance for at least one full traffic cycle before considering the change settled.
