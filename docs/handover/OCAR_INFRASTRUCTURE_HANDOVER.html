Section 01Scope, method and how to read this

This document describes the system as it is actually configured today, not as it was designed or intended. Every value, filename, job name and command was read directly out of the repository at the commit named on the cover page.

1.1 What this covers

The delivery pipeline (CI and CD), the AWS runtime environment, and the operational procedures for running it. It deliberately does not cover application-level product behaviour — ride matching, fare calculation, payment reconciliation — which is documented separately in CLAUDE.md and the module design specs under docs/superpowers/specs/.

1.2 Method and verifiability

Nothing here is asserted from memory or convention. Each factual claim is traceable to a file in the repository, and the relevant file path is named alongside it so any statement can be checked in under a minute. Where behaviour depends on an AWS semantic rather than on our code — for example what MinHealthyPercentage = 100 actually causes the Auto Scaling service to do — the claim was verified against AWS's own current documentation rather than inferred.

Section 17 lists what is not right. It is deliberately placed in the same document rather than omitted, because a handover that only describes the working parts is not a handover. Several items in it are consequential.

2.3 Isolation model

There are no private subnets, so isolation is enforced by security groups rather than by network placement. This is a deliberate trade — a NAT gateway costs roughly $32–45/month plus data processing charges, which is not justified at current scale. The security boundary is equivalent provided the groups are correct, and they are chained by group ID rather than by CIDR:

GroupInboundEffect
ocar-alb-sg:80, :443 from 0.0.0.0/0The only internet-reachable surface.
ocar-ec2-sg:4000 from ocar-alb-sg onlyInstances are unreachable from the internet despite holding public IPs.
ocar-<env>-rds-sg:5432 from ocar-ec2-sg onlyDatabase unreachable from anywhere but the fleet. publicly_accessible = false.
ocar-<env>-valkey-sg:6379 from ocar-ec2-sg onlyCache unreachable from anywhere but the fleet.

SSH is closed by default. var.ssh_debug_cidr defaults to null, which removes the rule entirely rather than leaving it open to a placeholder range. Administrative shell access, when required, is via SSM Session Manager — see §4.4.

2.4 Architectural decisions worth stating explicitly

DecisionReasoning
Modular monolith, not microservices One deployable unit with clean internal module boundaries (api/src/modules/*). At 1–2k rides/day with a team of this size, service decomposition adds network failure modes, distributed transactions and deployment coordination without removing any current constraint. The boundaries are already drawn in code, so extraction later is refactoring, not a rewrite.
EC2 + Compose, not ECS or Kubernetes The fleet is two to four identical instances running one application. An orchestrator's value is bin-packing heterogeneous workloads and managing large-scale scheduling, neither of which applies. ASG instance refresh already provides rolling, health-gated replacement.
Raw SQL, no ORM The platform is geospatially heavy (PostGIS ST_MakePoint/ST_MakeLine casts throughout) and uses append-only versioning patterns for rate cards that most ORMs default against. Documented at length in docs/architecture/2026-08-04-production-deployment-discussion-notes.md.
Single region The user base is Odisha. Multi-region adds replication lag, split-brain risk and roughly double the infrastructure cost for no latency benefit to the actual audience.
Workers co-located with the API Every instance runs every BullMQ worker. BullMQ's Redis-backed locking makes this safe. Splitting workers onto their own ASG is the correct move once queue load and request load need to scale independently; today they do not.

Section 04Access model and credentials

Nothing in the pipeline authenticates to AWS with a long-lived access key. All three GitHub Actions roles are assumed through OIDC federation, scoped by the workflow's own signed identity claim, and expire with the job.

4.1 The three CI roles

Defined in infra/terraform/github-oidc.tf. Each is trusted only for a specific GitHub OIDC subject claim, so a workflow cannot assume a role it was not designed for even if someone edits the workflow file.

Detail worth knowing

The deploy role's trust policy matches on environment:production, not on ref:refs/heads/main. This is not arbitrary — when a job declares environment:, GitHub changes the OIDC subject claim format. The ref-based condition was tried first, failed, and the actual rejected claim was read out of CloudTrail to determine the correct form. If you add a new deploy job, it must declare the same environment or the assume-role will fail.

4.2 The EC2 instance role

Instances assume ocar-<env>-ec2-role (infra/terraform/iam.tf). It grants ssm:GetParameter on exactly six named parameters and kms:Decrypt on the alias/aws/ssm key — nothing broader:

  • /ocar/<env>/image-tag — which image version to run
  • /ocar/<env>/ghcr-token — GHCR pull credential (SecureString)
  • /ocar/<env>/api-env — the application's entire environment file (SecureString)
  • /ocar/<env>/migration-database-url — direct DB URL for migrations (SecureString)
  • /ocar/<env>/docker-compose-prod — Compose file, Terraform-managed
  • /ocar/<env>/alloy-config — Alloy config, Terraform-managed

The AWS-managed AmazonSSMManagedInstanceCore policy is also attached. Its inline comment still describes it as temporary debugging access, which is now out of date — the deploy pipeline routes database migrations to a live instance through ssm:SendCommand, and that requires the instance to be a registered SSM managed instance. Removing this attachment would break every deploy. See gap G-04.

Section 06Continuous delivery

.github/workflows/deploy.yml. Three jobs — changes, build-push, deploy — chained by needs:. Triggered by workflow_run when the CI workflow completes on main, and gated on that run having concluded successfully.

6.1 Step-by-step, with the reasoning

Step 1 — Change detection

workflow_run triggers do not support on.paths: filtering, so this job implements it manually. It queries the Deploy workflow's own run history for the last successful deploy's commit SHA and diffs against that, falling back to HEAD^ only if no prior successful run exists.

Deployment proceeds only if the diff touches one of:

api/            pnpm-lock.yaml      pnpm-workspace.yaml
package.json    .github/workflows/deploy.yml

Two real incidents shaped this. First, an earlier version of the filter included infra/** and docker-compose.prod.yml; an infrastructure-only pull request that added an IAM role rebuilt the image and cycled the entire ASG for nothing. Neither path is ever copied into the image — api/Dockerfile only COPYs the lock files, the root package.json, and api/. Second, diffing against HEAD^ instead of the last deployed SHA silently skipped five commits when someone pushed six commits directly to main and only the last was documentation.

Step 2 — Build and push

Multi-stage build from api/Dockerfile. Four stages: install all dependencies, compile TypeScript, produce a symlink-free production node_modules via pnpm deploy --prod, then assemble a minimal node:22.16-alpine runtime image. The final image runs as the non-root node user and carries its own HEALTHCHECK.

Images are tagged sha-<short-sha>, plus latest on the default branch. The immutable SHA tag is what the deployment actually references — latest exists for convenience only and is never what an instance boots from.

Steps 4–5 — Migrations, and why they run through SSM

RDS is not publicly reachable; only the EC2 security group can open port 5432. A GitHub-hosted runner therefore cannot connect to the database directly. Rather than punch a hole in the security group or introduce a bastion, the workflow finds a live ASG instance and asks SSM to run the migration container there: 

docker run --rm --name db_migrate \
  -e MIGRATION_DATABASE_URL="$DB_URL" \
  --entrypoint node ghcr.io/<owner>/ocar-api:<tag> dist/db/migrate.js

Three properties of this arrangement are worth understanding:

  • No secret crosses the runner. The instance reads the database URL from SSM itself using its own IAM role. The command text sent by the workflow contains a parameter name, never a value.
  • Migrations run against the new image but before the rollout. The old application version is still serving every request while this happens, which means migrations must be backward-compatible with the currently-running code. Additive changes are safe; dropping or renaming a column that live code still reads is not.
  • --name db_migrate is load-bearing. Without an explicit name, Docker assigns a random one, cAdvisor discovers it as a new container, and every deploy permanently added active series to the Grafana Cloud metrics tenant. That caused a real cardinality incident on 19 August 2026. Alloy's relabel rules now keep only containers matching ocar_*, so this container is filtered out by name.
Idempotency

dist/db/migrate.js also runs on every container start via api/entrypoint.sh. So on a normal deploy the migration runner executes several times — once from this step, then once per replacement instance. This is safe because the runner skips already-applied files and serialises concurrent invocations with a pg_advisory_lock. The explicit step exists purely to gate the rollout on migration success rather than discovering a failure one instance at a time.

Steps 6–7 — Tag swap and refresh

The current value of /ocar/prod/image-tag is captured first — this is the rollback anchor, and capturing it before overwriting is the entire reason automatic rollback is possible. The new tag is then written, and an instance refresh is started. Note that instances read the tag only at boot; writing the parameter changes nothing until instances are replaced.

Steps 9–11 — Verification

CheckBudgetProves
Refresh status poll60 × 30 s ≈ 30 minAWS considers every replacement instance healthy in the target group.
GET /health8 × 5 sThe ALB is routing and an instance answers.
GET /api/v1/geo/cities3 × 3 sA real database-backed route returns real rows — the response body must contain "slug".

The certificate is issued for the domain, not for the ALB hostname, so verification is skipped deliberately at this step; the header is what makes the request route correctly.

The smoke test matters more than the health check. As documented in gap G-01, /health currently returns HTTP 200 even when the database is unreachable — so the smoke test is the only step in the pipeline that genuinely proves the database path works end to end.

Step 12 — Rollback

Any failure at steps 9, 10 or 11 restores the previously recorded tag and starts a second instance refresh, then exits non-zero. Two limits apply:

  • Migrations are not reverted. Schema changes are forward-only. If the migration itself is the fault, it must be fixed with a new migration, not undone.
  • Rollback depth is one. Only the immediately preceding tag is recorded. Going back further is a manual operation — procedure OPS-02.

Section 07Deployment strategy and its alternatives

The strategy is a rolling replacement with launch-before-terminate, implemented through EC2 Auto Scaling instance refresh. It is not blue/green and not canary. This section explains precisely what it does, and why the alternatives were not chosen.

7.1 What 100 / 100 actually means

Both asg.tf and the deploy workflow set MinHealthyPercentage = 100 and MaxHealthyPercentage = 100. Per AWS's documentation, setting the minimum healthy percentage to 100 changes the replacement method to launch before terminating: a replacement instance is launched and must pass health checks before the instance it replaces is terminated. Setting both values to 100 additionally constrains the group to replacing one instance at a time.

The practical consequence is that serving capacity never drops below the desired count during a deploy. Any other combination permits a dip — with min = 50 on a two-instance group, capacity can legitimately fall to one instance mid-deploy.

7.3 Why not blue/green

Blue/green stands up a complete parallel environment, shifts traffic at the load balancer, and keeps the old environment ready for an instant switch back. It is the right answer in several situations. None of them currently apply here, and one of them actively argues against it:

DimensionRolling refresh (current)Blue/green
Extra compute during deployOne additional instance, for a few minutesA full duplicate fleet, for the whole cutover window
Rollback speedMinutes — requires a second rolling refreshSeconds — flip the listener back
Database compatibilityBoth versions run simultaneously; migrations must be backward-compatibleSame constraint. Both fleets share one database — blue/green does not solve this
Long-lived WebSocketsDrains per instance, gradually, over the deregistration delayCutover disconnects every socket on the blue fleet at once
Moving partsOne AWS-native primitive already in use for scalingDuplicate target groups, listener-swap automation, environment-tracking state

The database row is the decisive one. The most commonly cited benefit of blue/green — instant, safe rollback — is materially weaker here because both fleets would share a single RDS instance. A schema change that breaks the old version breaks it whether that version is running on the green fleet or the blue one. The forward-only migration constraint documented in §6.1 is a property of sharing one database, not a property of rolling deploys, and switching strategies would not remove it.

The WebSocket row is the second. Ocar's traffic is dominated by long-lived Socket.io connections carrying live driver locations. A rolling replacement disconnects a fraction of clients per instance, spread over the deploy, and each reconnects to a healthy target within seconds. An atomic blue/green cutover disconnects every connected rider and driver simultaneously.

When to revisit

Blue/green becomes worth the additional machinery when deploys are frequent enough that multi-minute rollback is a genuine business cost, or when the fleet is large enough that a rolling replacement takes more than about half an hour. Neither is true at two to four instances. Canary — routing a weighted percentage to a new version via ALB weighted target groups — is the more natural next step, and would layer onto the existing setup without replacing it.

7.4 Deploys triggered by infrastructure changes

There is a second, easily-missed path to a rolling replacement. The ASG's launch_template block references aws_launch_template.api.latest_version — a real numeric version, not the literal string $Latest. Any Terraform change that produces a new launch template version (a new AMI, a different instance type, an edited boot script) therefore appears as a genuine diff on the ASG, and the instance_refresh block causes terraform apply to roll the whole fleet automatically.

Important

This means terraform apply can restart your entire production fleet. It is intended behaviour — without it, a launch template change would silently apply only to instances that happened to be replaced later for unrelated reasons. But it makes reading the plan output before applying non-optional. If the plan shows a change to aws_launch_template.api, expect a full rolling replacement.

Why there is no session stickiness

This is the single most counter-intuitive routing decision in the system, and it is correct. Socket.io is configured with transports: ['websocket'] only — HTTP long-polling is disabled entirely (api/src/websocket/socket.server.ts).

Long-polling is what normally forces sticky sessions: each poll is a separate HTTP request, and every one must land on the instance holding that client's Engine.IO session. A pure WebSocket upgrade has no such requirement — the connection is pinned to one instance for its entire lifetime by the TCP connection itself. Enabling stickiness would add a cookie and reduce distribution quality for zero benefit.

Cross-instance delivery is handled at the application layer instead. The @socket.io/redis-adapter publishes every room emit through Valkey, so io.to('ride:123').emit(...) reaches that ride's participants regardless of which instance each is connected to.

ALB idle timeout and Socket.io heartbeats

The ALB's idle timeout is at its default of 60 seconds — a connection with no bytes in either direction for 60 seconds is closed. Socket.io's server-side pingInterval is 25 seconds, so an idle WebSocket still exchanges Engine.IO heartbeat frames roughly every 25 seconds, comfortably inside the window. These two values are coupled. Raising pingInterval above 60 seconds, or lowering the ALB idle timeout below roughly 30, would start dropping idle connections. Change either only with the other in mind.

8.3 Maintenance mode

alb.tf defines a maintenance_mode boolean. Setting it creates a priority-1 listener rule matching /* that returns a fixed JSON 503 response, bypassing the target group entirely: 

terraform apply -var="environment=prod" -var maintenance_mode=true

This is the mechanism to use when the API fleet itself may be unavailable — during a botched instance refresh, for example — and the application-level Redis-backed maintenance flag cannot run because nothing is running. Because ELB health checks probe registered targets directly rather than routing through listener rules, this rule does not interfere with health checking, and instances continue to be evaluated normally while it is active.

Backing it with Valkey makes the limit hold across the fleet, and is a prerequisite for horizontal scaling that is easy to overlook.

Section 09Capacity: scaling out and in

Capacity moves three ways: automatically, within the configured bounds; manually, for a planned event; and structurally, by changing the bounds themselves. Each has a different mechanism, a different blast radius, and a different reversal path.

9.1 The automatic policy

aws_autoscaling_policy.request_count_tracking is a target-tracking policy on the predefined metric ALBRequestCountPerTarget with a target value of 1000. AWS manages the underlying CloudWatch alarms; there are no step adjustments to configure.

Read this carefully — the unit is not per second

ALBRequestCountPerTarget is a count per target over the metric period, and target tracking evaluates it on a one-minute period. A target value of 1000 therefore means 1000 requests per target per minute — roughly 16.7 requests per second, not 1000 requests per second. Misreading this by a factor of sixty in either direction produces either a fleet that never scales or one that scales constantly.

The value of 1000 is an estimate, explicitly labelled as such in the code comment. It has not been validated against real traffic. Retuning it is one of the primary deliverables of the load test in §16.

Why request count rather than CPU

For a request-driven Node.js API, CPU is a lagging indicator — by the time CPU is saturated, the event loop is already queuing and latency has already degraded. Request count per target rises before that, giving the roughly four to five minutes a new instance needs to boot, pull images and pass health checks. On t3 burstable instances there is a second reason: CPU credit exhaustion causes throttling that looks like low CPU utilisation, so a CPU-based policy can fail to scale precisely when the fleet is most degraded.

Discrepancy on record

The client-facing scale-readiness report dated 4 August 2026 states an autoscaling policy of min 3, max 5, scale on CPU > 70% sustained 3 min. The deployed configuration is min 2, max 4, on request count. The deployed version reflects later analysis and is the better choice for the reasons above, but the two documents disagree and the report has not been revised. Recorded as G-11.

Section 10Changing instance type and size

Instance type is a single Terraform variable. The mechanics are trivial; the judgement about which type, and the awareness that applying it restarts the fleet, are the parts that matter.

10.1 Where it is defined

var.instance_type in infra/terraform/variables.tf, default t3.medium. It is consumed in exactly one place — aws_launch_template.api in launch-template.tf. Nothing else references it, so changing it has one direct effect: a new launch template version.

Because the ASG pins version = aws_launch_template.api.latest_version, that new version is a real Terraform diff on the ASG, and the instance_refresh block turns the apply into a rolling replacement of the whole fleet (§7.4). This is the intended behaviour — it is how the change actually reaches running instances — but it must be expected rather than discovered.

10.2 Understanding the current choice

t3.medium is 2 vCPU / 4 GiB from AWS's burstable family. Burstable instances earn CPU credits while running below a baseline utilisation and spend them to burst above it. For t3.medium the baseline is 20% of each vCPU.

This suits the workload's shape: thousands of mostly-idle WebSocket connections punctuated by short bursts of work when GPS pings arrive or a ride is booked. Paying for fixed 24/7 performance to cover load that only spikes would be waste.

The risk this creates

Sustained high traffic — precisely a marketing surge — can exhaust the credit balance. The instance then throttles to baseline. The failure mode is a silent performance cliff, not a clean scale-out signal, and it can defeat CPU-based autoscaling (which is one reason this fleet scales on request count instead). Two mitigations exist: enable Unlimited burst mode, so the instance bursts past its credit balance for a small per-vCPU-hour surcharge instead of throttling; or move to a fixed-performance family. Unlimited mode is not currently enabled — recorded as G-16.

Architecture change — not a drop-in

Switching to any Graviton type (t4g, m6g, c7g) is not a one-variable change. Three things must move together, or instances will boot and fail to run the container:

  • The AMI filter in launch-template.tf is hardcoded to ubuntu-noble-24.04-amd64-server-* and must become arm64.
  • The container image is built for a single architecture. build-push in deploy.yml must produce a multi-architecture manifest (platforms: linux/amd64,linux/arm64 in docker/build-push-action), or the pull succeeds and exec fails.
  • Every sidecar image — Alloy, node-exporter, cAdvisor, postgres-exporter — must have an arm64 variant at the pinned tag. Verify each before switching.

Do this as its own deliberate change, validated on staging first. It is worthwhile — the saving is real — but it is a project, not an edit.

10.4 Sizing the container limits alongside the instance

Changing the instance type does not change the container's limits. ocar_api is capped at mem_limit: 2g, cpus: 1.5 in docker-compose.prod.yml regardless of what it runs on. Moving to an 8 GiB instance without raising mem_limit leaves 6 GiB unusable by the application.

Node 22 is container-aware and sizes its V8 heap from the cgroup limit, so no --max-old-space-size flag is needed — but it reads the container limit, not the instance's memory. The two must be changed together. Note also that docker-compose.prod.yml reaches instances via an SSM parameter sourced from the repo file, so a change to it requires a terraform apply to update the parameter and a fleet roll to take effect — it does not ride along with an application deploy.

Sizing from data, not guesswork

The current limits are explicitly a safety ceiling, not a tuned value. Their purpose is to stop an unbounded leak from taking down the whole instance by letting the kernel OOM-killer pick an arbitrary victim container. The cAdvisor "Per-Container Resource Usage" row on the ocar-overview Grafana dashboard reports working set, percentage of limit, CPU cores and OOM events per container. Size the final values from observed p95/p99 there once real or load-test traffic exists.

11.2 How secrets stay out of logs

The boot script runs under set -x, which traces variable assignments, not just commands. A plain GHCR_TOKEN=$(aws ssm get-parameter …) would print the resolved secret into /var/log/user-data.log. The script therefore disables tracing around both the assignment and the subsequent docker login, and re-enables it immediately after. This is worth preserving if the script is ever edited.

11.3 The known ergonomic problem

Whole-value overwrite

SSM supports only whole-value replacement. Changing one line in api-env means pulling the entire decrypted blob to a local file, editing it by hand, and pushing the whole thing back. During the Redis-to-Valkey migration on 12 August 2026 this caused a real incident: a hand edit changed the REDIS_URL scheme but missed the hostname, because the whole value has to be reviewed at once instead of editing one key.

A per-key secrets manager would remove this failure mode. It is on the backlog and deliberately not urgent — SSM SecureString is a legitimate credential store, the problem is ergonomics rather than security. Procedure OPS-06 gives the safe sequence for editing it today.

Why noeviction is not optional

BullMQ stores job payloads in Redis. The ElastiCache default parameter group uses volatile-lru, which evicts keys under memory pressure — meaning queued jobs (notifications, GPS flushes, settlements) can silently disappear. This exact misconfiguration was observed on the previous Redis Cloud instance. Do not change this parameter.

Two open items

Transit encryption is in preferred mode, which accepts both rediss:// and plaintext redis://. This was the correct choice for migrating without a hard cutover, but it should be flipped to required once every instance is confirmed on rediss://. Recorded as G-12.

The cache is a single point of failure. There is no replica and automatic failover is disabled. If the node fails, Socket.io fan-out, BullMQ and rate limiting all stop. Cache contents are genuinely disposable, so the recovery is a node replacement rather than a data loss event — but it is an outage. Adding a replica is a one-line change when the availability requirement justifies the cost.

OPS-01 Deploy application code Routine · automatic · ~10–15 min

Blast radius: production fleet rolled one instance at a time. No capacity dip. Reversal: automatic on failure; manual via OPS-02.

  1. Merge to main. Nothing else is required — the pipeline is fully automatic.
  2. Watch the CI workflow. All seven jobs must pass or Deploy never starts.
  3. Watch the Deploy workflow. If the Detect relevant changes job reports relevant=false, the change did not touch anything that reaches the image and no deploy is needed — this is correct behaviour, not a fault.
  4. Observe the rollout while it runs: 
    watch -n 15 'aws autoscaling describe-instance-refreshes \
  --auto-scaling-group-name <ASG_NAME> --max-records 1 \
  --query "InstanceRefreshes[0].{Status:Status,Pct:PercentageComplete}" --output table'
  5. Confirm afterwards: 
    curl -s https://ocar-api.clienttesting.in/health | jq
curl -s https://ocar-api.clienttesting.in/api/v1/geo/cities | jq '.[0]'

If a migration is involved: it runs before any instance is replaced and gates the rollout. It must be backward-compatible with the currently-running code, because the old version keeps serving traffic throughout — see §6.1.

OPS-02 Roll back to a specific image version Emergency · manual · ~10–15 min

Blast radius: full fleet roll. Reversal: repeat with the newer tag.

  1. Identify the target tag. Tags are sha-<short-sha> and are listed on the GHCR package page, or in the Docker metadata step of a previous Deploy run.
  2. Record what is currently deployed, so this step is itself reversible: 
    aws ssm get-parameter --name /ocar/prod/image-tag --query 'Parameter.Value' --output text
  3. Point the parameter at the target version: 
    aws ssm put-parameter --name /ocar/prod/image-tag \
  --type String --value "sha-abc1234" --overwrite
  4. Roll the fleet so instances actually pick it up: 
    aws autoscaling start-instance-refresh \
  --auto-scaling-group-name <ASG_NAME> \
  --preferences '{"MinHealthyPercentage":100,"MaxHealthyPercentage":100}'
  5. Verify as in OPS-01 step 5.
Migrations are not reverted

Schema changes are forward-only. Rolling the image back does not undo a migration. If the migration is the fault, the old code will now be running against a newer schema — which may be worse than the problem you are fixing. Fix forward with a new migration instead.

OPS-03 Enable or disable maintenance mode Emergency · manual · ~1–2 min

Blast radius: every request receives HTTP 503 immediately. Reversal: re-apply with the flag false.

  1. Enable: 
    terraform apply -var="environment=prod" -var maintenance_mode=true
  2. Confirm the fixed response is being served: 
    curl -i https://ocar-api.clienttesting.in/api/v1/geo/cities

    Expect 503 with "code":"MAINTENANCE_MODE".

  3. Disable when finished: 
    terraform apply -var="environment=prod" -var maintenance_mode=false

OPS-04 Temporarily add capacity for a known event Planned · manual · ~5 min · creates drift

Blast radius: adds instances and cost. Reversal: mandatory — see step 4.

  1. Check the current bounds: 
    aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names <ASG_NAME> \
  --query 'AutoScalingGroups[0].{Min:MinSize,Desired:DesiredCapacity,Max:MaxSize}' --output table
  2. Raise desired capacity. It must stay within the existing min/max, so raise --max-size in the same call if you need to exceed 4: 
    aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name <ASG_NAME> \
  --min-size 4 --desired-capacity 4 --max-size 6

    Raising --min-size too is deliberate: it stops the target-tracking policy from immediately scaling back in while traffic is still low, just before the event starts.

  3. Confirm the new instances reach InService — typically four to five minutes: 
    aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names <ASG_NAME> \
  --query 'AutoScalingGroups[0].Instances[].{Id:InstanceId,State:LifecycleState,Health:HealthStatus}' \

  4. Restore afterwards. Either repeat step 2 with the original values, or run terraform apply, which will reset them to whatever asg.tf declares.
This creates Terraform drift on purpose

Blast radius: one instance. Reversal: none needed — the ASG relaunches automatically.

  1. Identify it: 
    aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names <ASG_NAME> \
  --query 'AutoScalingGroups[0].Instances[].{Id:InstanceId,State:LifecycleState,Health:HealthStatus,AZ:AvailabilityZone}' \
  --output table
  2. Look before you kill it — the cause is usually in the boot log or the container log: 
    aws ssm start-session --target <INSTANCE_ID>
sudo tail -100 /var/log/user-data.log
sudo docker ps -a
sudo docker logs --tail 200 ocar_api
  3. Terminate it and let the ASG replace it. --should-decrement-desired-capacity false is what makes the replacement happen: 
    aws autoscaling terminate-instance-in-auto-scaling-group \
  --instance-id <INSTANCE_ID> \
  --no-should-decrement-desired-capacity
  4. Confirm the replacement reaches InService and Healthy. Allow at least the 240-second grace period plus three 15-second health checks.

If replacements repeatedly fail to become healthy, the problem is systemic — a bad image, a broken SSM parameter, or an unreachable dependency. Go to OPS-12 rather than cycling instances.

OPS-12 Diagnose a failed or stuck deploy Incident · investigation

Blast radius: read-only until you choose an action.

  1. Locate the failing step in the Deploy workflow run. The step name maps directly onto Figure 4.
  2. Migration step failed → the rollout never started and production is untouched, still running the previous version. Read the captured stdout/stderr in the workflow log. Fix the migration and merge again. Do not attempt to force the rollout past it.
  3. Refresh timed out or failed → replacement instances are not becoming healthy: 
    aws autoscaling describe-instance-refreshes \
  --auto-scaling-group-name <ASG_NAME> --max-records 1 \
  --query 'InstanceRefreshes[0].{Status:Status,Reason:StatusReason,Pct:PercentageComplete}'
    Then shell into a failing instance and read /var/log/user-data.log. The usual causes are a GHCR pull failure (expired ghcr-token), a malformed api-env, or the application exiting at startup because it cannot reach RDS or Valkey.
  4. Health check failed but the refresh succeeded → instances are healthy at the target group but the ALB is not serving correctly. Check target health directly: 
    aws elbv2 describe-target-health --target-group-arn <TG_ARN>
  5. Smoke test failed but health passed → this is the important case. It means the process is alive but the database path is broken, which /health does not currently detect (G-01). Check RDS availability, the security group, and DATABASE_URL in api-env.
  6. To stop an in-progress refresh: 
    aws autoscaling cancel-instance-refresh --auto-scaling-group-name <ASG_NAME>

    Cancelling leaves the group in a mixed state — some instances on the new version, some on the old. Follow immediately with OPS-02 to converge on a known-good tag.

Section 15Failure modes and recovery

What breaks, what it looks like, and what to do. Ordered by how likely each is to occur.

Valkey node fails Real-time updates stop; BullMQ stalls; rate limiting fails open or closed None — single node, failover disabled Replace the node. Cache contents are disposable; this is an outage, not data loss.

Entire AZ fails Half the fleet unhealthy ALB routes to the surviving AZ; ASG launches replacements there Monitor. If RDS was in the failed AZ, the database is down until AWS recovers it — single-AZ is an accepted risk.
Grafana Cloud cap exceeded Billing-usage alert at 85%; metrics or logs start being dropped Alert fires Review cardinality (§13.2) before assuming an upgrade is needed. Both prior incidents were cardinality, not genuine volume.

The pattern worth internalising

Every failure the platform recovers from automatically is one where an instance is the failing unit. Every failure requiring manual intervention is one where a shared singleton fails — the Valkey node, the RDS instance, an SSM parameter. That is the accurate summary of this architecture's resilience profile: the compute tier is genuinely redundant; the data tier is not.

17.2 Detail on the high-severity items

G-01 — The health endpoint cannot fail

api/src/app.ts checks database and Redis connectivity, reports the result in the response body, and then unconditionally returns HTTP 200: 

const [dbOk, redisOk] = await Promise.all([testConnection(), testRedis()])
res.status(200).json({ status: 'ok', db: dbOk ? 'ok' : 'error', … })

The ALB target group matches on 200. An instance whose database connection has failed therefore remains healthy and continues receiving traffic indefinitely. The ASG will not replace it. The deploy pipeline's health check will pass.

The smoke test against /api/v1/geo/cities is currently the only automated check that would catch this, and it runs once per deploy rather than continuously. Suggested fix: return 503 when dbOk is false, keeping the diagnostic body intact. Consider whether Redis failure should also fail the check — it degrades real-time delivery but leaves core HTTP working, so it may warrant a separate readiness endpoint rather than the same one.

G-02 — Staging cannot be provisioned through CI

rds.tf was added to the shared configuration, but the ocar-prod-gha-staging role's policy in github-oidc.tf grants only ec2, elasticloadbalancing, autoscaling, elasticache and acm. There is no rds:* statement, and no secretsmanager:* — which manage_master_user_password also requires.

A staging apply will proceed until it reaches the database resources and then fail on AccessDenied. Because this is the environment the load test depends on, this blocks OPS-09, which in turn blocks the load test, which in turn blocks the capacity validation the entire scale-readiness report defers to.

G-05 / G-06 — Missing approval gates

Three protections referenced in the workflows do not actually exist:

DeclaredRealityConsequence

The exact gh api commands to close each are documented in CLAUDE.md under "Pending Ops Actions". This is the single highest-value item on this list for whoever holds admin rights — it is minutes of work and closes three distinct paths to unreviewed production change.

G-14 — Admin TOTP enforcement is bypassed

api/src/middleware/auth.middleware.ts line 125: 

// TODO(SHIP-BLOCKER): hardcoded bypass, see TOTP_DEV_NOTE.md — remove before shipping
const mustEnrollTotp = false && MANDATORY_TOTP_ROLES.has(adminRole) && !totpEnabled

The leading false && short-circuits the entire expression, so super_admin and finance_admin accounts are never required to enrol in two-factor authentication despite the surrounding logic being complete and correct. The enrolment endpoints work; the enforcement is simply switched off. The comment marks it as a ship blocker. It is flagged here because these are the roles with the broadest access in the system.

G-13 — Test coverage

Five test files exist in the API — four covering ride assignment and broadcast, one covering maintenance middleware. There are none for payments, wallet, settlements, authentication, OTP, safety or ride chat. vitest and @vitest/coverage-v8 are installed and pnpm test:coverage is defined, but CI runs pnpm test with no threshold.

This is worth stating plainly: the delivery pipeline is well-built and the gates are structurally sound, but a gate is only as strong as the checks behind it. Payments and authentication are the two areas where a regression is most expensive and where there is currently no automated protection at all.
