Round-Trip Rate Cards

Why every nearby outstation destination is currently priced the same, and how to correct it from the admin portal.

Ocar · Prepared for operations and pricing · 31 August 2026
Formula verified against api/src/lib/fare.ts (round-trip branch); seeded values against 016_seed.sql and 074_round_trip_package_billing.sql.

Reported issue

“Round trip Outstation ride fares showing same for Bhubaneswar and Puri also. So it’s not calculating properly.”

Summary

The calculation is correct. The configuration is not. Round trips are billed on a guaranteed-minimum-kilometre package — the same model Ola Outstation and comparable operators use. That package is currently set to 250 km per day for every vehicle category, a placeholder inserted during setup and never replaced with real numbers. The practical effect: every destination within roughly 125 km of the pickup point returns an identical fare, because the whole round trip fits inside the package. The fix is a data change in the admin portal — no code change, no deployment.

1. Which ride type covers which journey

This document concerns round trips only. Ocar has three ride types and they serve different journeys, so it is worth being precise about the boundary before looking at fares.

Ride typeServesBilling basis
RentalJourneys that begin and end inside the same city zone Hourly/kilometre packages from rental_packages — a separate configuration, not covered here.
One wayIntercity, single leg Per kilometre plus per minute.
Round tripIntercity, out and back Guaranteed-minimum-kilometre package plus driver allowance. This document.

A journey is treated as intercity only when pickup and drop do not both fall inside the same city boundary. That check lives in classifyTrip(), which returns either in_city or outstation.

Bhubaneswar, Cuttack and Khordha are one zone

These three are deliberately configured as a single merged city boundary, not three separate cities. Any journey between them therefore classifies as in_city and is served by rental, not by round trip. They are consequently not used as examples anywhere in this document — a Bhubaneswar–Cuttack round trip is not an outstation booking and is not priced by the rate cards discussed here.

Every route used below is a genuine outstation destination: a separately configured city outside that merged zone.

2. How a round-trip fare is built

A round-trip outstation booking is not billed purely per kilometre driven. It is billed as a package: a guaranteed minimum distance per day that the customer pays for whether or not they travel that far, plus a flat daily allowance for the driver, plus any distance driven beyond the package (“overage”).

The package exists to protect the driver. A driver who commits a full day to an outstation trip should not be paid as though it were a short hop. The package sets a floor under that day’s earnings.

# api/src/lib/fare.ts — round_trip branch

days = max(1, ceil(trip_hours / 24)) // trip_hours is floored at 4 upstream
packageKm = days × km_per_day
overageKm = max(0, estimated_km − packageKm)

distance_fare = packageKm × rate_per_km
overage_fare = overageKm × rate_per_km
metered = distance_fare + overage_fare
floored = max(metered, min_fare)
subtotal = floored + stop_fare + (days × driver_allowance_per_day)
total = subtotal × surge_multiplier

# The two metered lines reduce to a single idea:
# metered = max(estimated_km, packageKm) × rate_per_km
# You pay for the package, or for the real distance — whichever is larger.

Two details that matter and are easy to miss:

  • estimated_km is the total to-and-fro distance, not the one-way leg. Puri is a 64 km leg, so estimated_km = 128. The doubling happens in pricing.service.ts before the fare engine runs.
  • Surge multiplies the whole subtotal, including the driver allowance — not just the distance component.

3. Why nearby destinations all return the same fare

With km_per_day = 250 on a single-day trip, the package is 250 km of round-trip distance. That covers any destination up to 125 km away. Puri, Jajpur and Paradeep are all inside that radius, so all three are billed for the full 250 km package, none generates overage, and the actual distance never enters the calculation.

4. Is this pricing model correct?

Yes. The guaranteed-minimum-kilometre package is the standard commercial model for outstation cabs in India, not an invention of this platform. Ola Outstation bills a minimum of 250 km per day for sedans at roughly ₹11–15/km, with a mandatory driver allowance (batta) of ₹300–500 per day on top, plus GST and surge. Savaari and other established operators price the same way.

The distinction that matters

The 250 km/day figure is genuine industry practice — for the trips it was designed for. It protects a driver on a long interstate run of 400 km or more, often spanning several days. It was never intended for a 64 km regional hop. Ocar inherited the number without inheriting the context: the model is right, the parameter is wrong for this market. Odisha’s coastal corridor puts most demand well inside a 125 km radius, which is precisely the range the current setting flattens.

Cross-check against the live market

Published fares for a Bhubaneswar–Puri same-day round trip by sedan sit in the ₹1,700–₹2,200 band. Ocar currently quotes ₹3,550 — roughly 60–100 % above the market.

5. Choosing the right package size

The rule: the package must be smaller than the shortest round trip you actually sell. Only then does real distance drive the price. If the package is larger, every trip beneath it collapses to the same fare. Ocar’s shortest outstation round trip is Puri at 128 km, so the package must sit below 128.

Read this table carefully

At or below 128 km the fares stop changing. Once the package is smaller than every real route, actual distance is doing all the work and the exact package value no longer affects these trips. Its only remaining job is to protect the driver on an unusually short booking. That means you do not need to find a precise number — you need a number safely below your shortest sellable round trip.

Note also that Balasore never moves: ₹5,396 at every setting. Long trips already bill on real distance and are unaffected by this change.

A trap worth avoiding

Lowering the package from 250 to 200 would look like a fix and would not be one. Puri, Jajpur and Paradeep would still all fall inside a 200 km package and still bill identically — the original complaint, reproduced at a lower price. Even 196 leaves Puri and Jajpur tied. Always check a proposed value against your shortest route, not your longest.

This is a revenue change, not only a bug fix

Correcting the package cuts the quoted sedan Puri fare from ₹3,550 to ₹1,964 — about 45 % lower — and Puri is likely the highest-volume outstation route on the platform. That is the intended outcome, since the current figure is well above market and was never deliberately chosen. It should nonetheless be signed off by whoever owns pricing before it is applied, not treated as a silent technical correction.

7. How to change it

The values live in the rate_cards table and are editable from the admin portal. No deployment, no migration, no engineering involvement.

  1. Sign in to the admin portal and open Config → Rate Cards (/config/rate-cards).
  2. Find the row for the vehicle category you want, with ride type Round Trip, and open it. The dialog is titled Update <Category> · Round Trip.
  3. Leave City as All Cities (Global Default) unless you specifically want a single-city override — see the caution below.
  4. Edit Package KM/day. This is km_per_day. The field shows the current value beneath it as was 250.
  5. Adjust Driver Allowance/day (₹) if required. This is driver_allowance_per_day.
  6. Fill in Change Reason — mandatory, and written to the rate-card history as the audit record for this change.
  7. Save. Repeat for each of the five categories.
What happens when you save

Nothing is overwritten. Rate cards are versioned: saving expires the current row and inserts a new one, so previous pricing stays on record. The dialog states this directly — “Creates a new rate card and expires the current one. All future rides use the new rate.”

Rides already booked are unaffected. Every booking freezes its own fare breakdown in a fare snapshot at the moment of booking, so in-flight and completed rides keep the price the customer agreed to. Only estimates requested after the save use the new values.

Caution: a city override will not solve this

The City dropdown scopes a rate card to a single city, and it is matched on the pickup city only — the destination is not part of the lookup. A Bhubaneswar override therefore applies identically to a Bhubaneswar–Puri trip and a Bhubaneswar–Balasore trip. City overrides answer “fares starting in Berhampur differ from fares starting in Bhubaneswar”, not “further destinations should cost more”. Distance already handles the second case once the package is set correctly.

How to verify the fix

  1. Save the new values for one category — Sedan is easiest to check.
  2. In the rider app, request round-trip estimates to two different outstation destinations at clearly different distances — for example Puri and Paradeep.
  3. Confirm they now return different fares, and that Puri lands near the ₹1,964 shown above. Small differences are expected: the real routed distance will not be exactly 128 km, and any active surge multiplies the total.
  4. Repeat for the remaining categories.
One related item, listed separately

The second issue reported the same day — Khordha pickups classifying as outstation rather than in-city — is a different and unrelated fault, caused by a city-boundary migration overwriting an earlier deliberate merged boundary. It requires a code change and a deployment, and is not affected by anything in this document. Once corrected, Khordha journeys to Bhubaneswar or Cuttack return to being in-city and are served by rental rather than round trip.
