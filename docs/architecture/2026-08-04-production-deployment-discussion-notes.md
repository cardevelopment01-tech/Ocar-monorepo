## Why EC2 `t3.medium` (burstable) over a fixed-performance instance

`t3` is AWS's burstable family — baseline CPU% (~20% of 2 vCPUs for `t3.medium`) plus burst capacity
via accumulated CPU credits, priced well below fixed-performance families (`m5`/`c5`) for the same
vCPU/RAM.

**Fits this load:** Socket.io connections sit mostly idle between GPS pings, and 1-2k rides/day is a
low steady request rate — low baseline utilization with occasional spikes, exactly the pattern t3 is
priced for. Paying for fixed 24/7 performance to cover load that only spikes occasionally would be
wasted spend.

**The risk:** burstable credits can run out under sustained high traffic, causing throttling back to
baseline CPU — the worst failure mode during a marketing surge (silent performance cliff, not a clean
scale-out).

**Mitigations (both should be in place):**
1. Enable **`t3.medium` "Unlimited" burst mode** — bursts past the credit balance for a small
   per-vCPU-hour surcharge instead of throttling.
2. **Load test (see main report, checklist step 13)** is the real verification — if CPU credit balance
   drains during the simulated 6k-socket burst, that's the signal to move to `m5.large` (fixed
   performance, no credit mechanic) instead of trusting the estimate blind.

## Grafana stack (Loki) vs ELK — reaffirmed

**Decision: Grafana Cloud + Loki, not ELK/OpenSearch.** (Same conclusion as §06 of the main report,
restated here because it came up again.)

- **Resource cost:** Elasticsearch is JVM-based and full-text indexes everything — heavy CPU/RAM even
  at moderate volume. Loki only indexes metadata/labels, a fraction of the footprint. At 5-6k users,
  that indexing weight buys nothing.
- **Ops burden:** ELK needs someone tuning shards/JVM heap/cluster health. No dedicated DevOps
  headcount for that here. Grafana Cloud free tier needs none of it.
- **Already the plan:** Pino logs, Prometheus metrics, and OpenTelemetry traces already route through
  one Alloy agent into Grafana Cloud — Loki is just the logs piece of that same pipeline. ELK would be
  a second, unrelated system to run.
- **Cost:** Grafana Cloud free tier covers current volume entirely. Managed Elasticsearch (AWS
  OpenSearch) starts ~$25/mo and climbs fast with retention/volume.
- **When ELK would actually win:** complex full-text search across huge log volumes (millions of
  lines/day, many services) — not this platform's log volume, and won't be for a long while.

## Why no ORM (raised as "ODM")

Correction made in-thread: ODM (Object-Document Mapper, e.g. Mongoose) is for document DBs like
MongoDB. This project runs PostgreSQL, so ODM doesn't apply — the real question is ORM (Prisma,
TypeORM, Sequelize, Drizzle), and the answer is: **none used, raw parameterized SQL via `pg` pool
everywhere** (`api/src/db/client.ts`, e.g. `rides.repository.ts`).

Reasoning, grounded in what's actually in the codebase:

- **PostGIS needs precise control** — `ST_MakePoint`/`ST_SetSRID`/`ST_MakeLine` geography casts.
  Most ORMs handle PostGIS poorly or force raw SQL anyway. Given how geospatial-heavy this platform is
  (driver matching, route distance, city geofencing), an ORM would be fought more than used.
- **Rate card versioning** (`CLAUDE.md`: never `UPDATE rate_cards`, always INSERT new + close out old
  via `effective_to`) is an explicit audit-trail pattern most ORMs default against (they want
  update-in-place).
- **Deferred FK pattern** (column added before the referenced table exists, FK constraint added later
  in a subsequent migration) doesn't map cleanly onto ORM schema/migration tooling.
- **Explicit security posture** — the project's own rule ("SQL injection: only hardcoded column names
  in dynamic UPDATE builders") reads as wanting every query visible and controlled, not generated by an
  abstraction layer.

**Tradeoff accepted:** more boilerplate per query, no auto-generated types from schema, no automatic
migration diffing. **Gained:** full control over PostGIS query shape, explicit per-query performance
tuning (relevant to the pending DB load-test prep), no ORM upgrade risk on top of everything else in
flight.

**Recommendation if this comes up again:** keep it this way. Introducing an ORM now means rewriting
the geo and pricing modules to fit its assumptions, for a boilerplate-reduction benefit that matters
less than the control currently held over PostGIS and versioning behavior.

## Sentry data region — EU, not US, with PII scrubbing

**Trigger:** client raised that Sentry has no India data region (confirmed: only US and Frankfurt/EU,
choice is permanent at org creation).

**Decision: stay on managed Sentry Cloud, EU (Frankfurt) region** — not self-hosted (GlitchTip was
evaluated and rejected per the client's stated preference against self-hosting overhead).

Reasoning:
- **Latency is a non-issue.** The Sentry SDK sends error events asynchronously, after the response has
  already gone back to the user — it's never in the request/response path. Region location affects how
  fast the *dev team* sees an error in the dashboard, not app response time for end users.
- **Sentry is the Indian-market standard too** — widely used by Indian startups once past ~10
  engineers, not an unusual choice.
- **Residency is a compliance question, not a performance one.** Only becomes a hard blocker if the
  client has an actual regulatory mandate (e.g. certain RBI-regulated fintech data categories) or an
  explicit legal policy against data leaving India. This platform's payment processing runs through
  Razorpay (raw card/payment data isn't stored in app error logs), so this usually isn't a hard blocker
  for error-tracking data specifically — **still worth confirming directly with the client whether they
  have an actual compliance mandate vs. a preference**, since that answer flips the self-host decision.
- **EU over US** as the safer default compliance posture (GDPR-aligned) when there's no explicit India
  requirement.

**Hardening regardless of region:** use the Sentry SDK's `beforeSend` hook to scrub PII (phone numbers,
exact GPS coordinates, payment references) out of error payloads before they're sent. Reduces exposure
regardless of where the data physically sits, and is good practice independent of this decision.

**If the client later confirms a hard compliance mandate:** revisit self-hosted GlitchTip in ap-south-1
(evaluated above) as the fallback — SDK-compatible, no application code change needed, only the DSN
target changes.

## Sentry free tier vs paid — is it generous enough

**Verdict: fine for build-out/testing, not for the live campaign.** Two real constraints, not just
event volume:

- **Volume ceiling has a bad failure mode.** Free tier is 5,000 events/month (~7/hour average, fine for
  a healthy app). But Sentry counts every *occurrence*, not unique bugs — one recurring issue hit
  repeatedly during a traffic spike (exactly what the marketing surge risks) can exhaust the monthly
  quota in minutes, causing Sentry to drop/rate-limit events right when an incident is happening.
- **Single-user limit is the bigger practical wall.** Free tier is one login, period — doesn't work once
  more than one person on the team needs error visibility.

**Decision:** stay on free tier through build/testing, **upgrade to the Team plan ($26/mo annual, 50k
events, unlimited users) before the marketing campaign goes live.** Cheap relative to the ad spend
driving the traffic, and removes both constraints at the exact moment they'd otherwise bite.
